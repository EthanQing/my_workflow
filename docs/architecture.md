# Architecture

Task baseline: AEGIS-001 / P1, desktop DSH 0.2.1-rc.2. This document describes implemented configuration, not a separate orchestration engine.

`package.json` declares an ordered `dsh.bundle.patch` list. Each YAML file inserts one `@deepseek-ai/dsh-agent-preset` declaration. Lead mounts one `@deepseek-ai/dsh-tool-subagent` consumer with `toolName: aegis_delegate`, a default Planner preset, a six-id `allowedAgentPresets` enum, and `maxDepth: 1`; each call selects the child via `agent_preset`. Children contain no delegation tools. Host services remain owned by DSH; the bundle neither replaces the registry nor changes its default preset.

The local in-process spawn provider's `prepareContinuable` capability selects the official managed local lifecycle. Each child owns a session ID and its own prompt/tool composition. Completion releases its active instance. Official parent catalog projections and JSONL session persistence provide identity and restoration. `list_agents` reports running/inactive children; `send_message` accepts either state. Persistent history and a permanently running process are different things.

Planner, Coder, Reviewer and Git Operator mount the official `@deepseek-ai/dsh-tool-subagent-control` package, which provides adjacent `send_message` (parent ↔ direct child) and `interrupt_agent`, but no `list_agents` and no delegation. Knowledge Curator and Project Mentor are completion-only and do not mount the control package. A chat-capable child receives its parent id in the initial task guidance and can send a blocker, decision request or material risk while working; the completion notice remains the single final delivery. Messaging is exact-ID and adjacent; there is no broadcast or polling. `session_event_read` is recovery-only. The control package's `interrupt_agent` cannot target the parent or siblings and is inert in child presets without delegation.

Lead keeps the complete task envelope in conversation: task ID, plan version, workspace, initial commit/status or non-Git baseline, existing edits, original request/clarifications, approval evidence/scope, full Planner plan, current code state, checks and cumulative rework. It sends only a compact execution brief to executors; the full plan stays in the Planner session, and Reviewer receives the diff, acceptance criteria and existing check evidence instead of the full plan. This is coordination context, not a custom persisted database. Role reuse preserves useful investigation, never authorization across tasks.

Task tiering is prompt-level routing, not a new engine. Small tasks use a Lead-authored versioned brief, user approval, Coder (or Curator for a small knowledge-only update) and a Lead final check; Planner and independent Reviewer are skipped. Normal tasks use Planner, approval, Coder, optional Curator, independent Reviewer and Lead check. High-risk tasks add only the genuinely necessary extra verification. Classification is conservative; uncertainty or scope growth reclassifies and requires new approval. No new agent, tool, approval step or permission is introduced.

Recovery first consults the existing catalog and workspace-authorized raw session reads. Desktop defaults to `openAt: never`, so full-text search is optional, never a recovery prerequisite. On disabled search, read the original child with `session_event_read`, `seq: 0, after: 50`; advance from the last returned sequence, inspect subsequent windows, and fully read the identified result event. No index is enabled and no replacement child is spawned. Completed, still-valid work is reused. Missing original evidence is reported before repeat execution; file changes or Git commits are inspected before retries. Cold restoration needs official session storage and currently registered matching preset IDs. Same-workspace history tools require exact cwd equality. Restoring under a new bundle version loads its current preset definition.

Read-only role tool sets omit shell/write/edit. Coder has file writes and shell; Curator has file writes without shell. Curator's documentation-only scope, Coder's no-knowledge/no-Git rules, Lead's investigation-only shell use, writer serialization, approval gates and three-round maximum are prompt instructions. They are not strict security enforcement. No custom command interceptor is included. An untrusted/misbehaving model requires host sandbox and permissions for stronger guarantees.

On Windows, the verified host is DSH desktop 0.2.1-rc.2 with `dsh-gitbash-shell` 0.38.5. The plugin withdraws `pwsh-sandbox`, installs a Git Bash `ctx.shell` executor (`bash.exe -c`), and, for an agent whose composed face has `pwsh` but no `bash`, mounts the official `tool-bash` and denies the fake `pwsh`. The three shell-role presets keep the official per-platform tool row because it is the plugin's input; a static flip to `tool-bash` is unsafe on Windows profiles without that executor. This is host integration, not a bundle-owned shell implementation. The prompts also carry the temporary-artifact and minimal-verification rules; those remain behavioral, not enforced by DSH.

`tests/` and `scripts/test-runtime.mjs` are development-only and excluded from the published package whitelist. They exercise the installed desktop's actual Loader, preset registry, Agent loop, model-visible tools, subagent manager, spawn provider, persistence and SQLite history query with a deterministic model adapter. No product runtime JavaScript is shipped.
